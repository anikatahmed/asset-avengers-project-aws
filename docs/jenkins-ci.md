# Jenkins Docker isolation

See [the testing guide](testing-guide.md) for what each suite checks, why it is
needed, how it runs, and which checks remain opt-in or unverified.

Jenkins uses `deployment/ci/ci.compose.yml` through `scripts/ci-compose.sh`.
Development continues to use the root `docker-compose.yml` and the existing
start/stop scripts. The CI Compose file covers client, trading API, authentication and their databases.
The additional staff/reporting image and integration stages are described below.

## What one build owns

The initialization stage generates a random project such as
`endgame-ci-0123456789abcdef`. Compose gives its containers, network and two database
volumes that project prefix. Another build receives a different project even on
the same agent. There are no fixed container/network names or published host ports.
Services reach each other by Compose service name inside their own network.

Trading and authentication data use temporary named volumes. SQL schema and seed
files are mounted read-only from the checkout and initialize those empty volumes.
CI never mounts the development database directory in the user's home folder.
Application image names generated by Compose are also project scoped. Cleanup
removes containers, networks and volumes; it does not prune Docker's image/build cache.

For example, builds A and B can each have a service called `postgres` listening on
5432 inside their separate networks without competing for the host's port 5432.
Destroying A's volume does not destroy B's volume or a saved development database.

## Initialization and cleanup

Jenkins writes its existing root `.env`, generates `CI_PROJECT_NAME`, then invokes
`bash scripts/ci-compose.sh init`. This validates the standalone configuration and
writes a project-specific receipt under ignored `.ci/`. Jenkins sets
`CI_ENV_INITIALIZED=true` only after that succeeds.

Every build, start, status and log command goes through the helper. The helper
requires a valid CI project name and a matching initialization receipt. The Jenkins
post stage skips cleanup if initialization did not succeed. Otherwise `cleanup`
executes `docker compose` with the explicit CI file and project, followed by
`down --volumes --remove-orphans`. The receipt is removed only after successful
cleanup, so a failed cleanup can be retried. Container logs are captured before
cleanup for failure notifications. Even partial startup failures can be
cleaned up once initialized. No daemon-wide deletion or container-name search runs.

These guards prevent accidental cleanup of another stack. They are not a security
boundary against untrusted code with Docker daemon access. Jenkins jobs still need
trusted execution and appropriately controlled agents.

Use the `docker compose` plugin on development and CI hosts. This configuration needs no override
reset tags, `--wait`, or `--quiet`. The exact installed VM version should still be
validated before rollout.

## Scope of this update

CI checks now include resource isolation, required failure propagation, coverage,
PR routes, service readiness and staff/reporting builds/integration. The CI-only
deployment boundary and remaining browser/SSO test limits are described below. Future stages must use the same helper rather than
calling the development Compose file directly.

## Required checks and failure handling

`Jenkinsfile` calls `bash scripts/ci-checks.sh secrets`, `services`, and `sonar`
as required steps. The script explicitly uses Bash with `set -euo pipefail`:
failed commands stop the stage, including commands whose output is piped to `tee`.
A successful log write cannot turn a failed check into a successful build.
The service command group stops immediately on a failed startup instead of running
status commands and replacing the original failure with a successful status result.

For example, if a Docker build exits with code 17, the services check retains its
output in `services-output.txt` and returns 17 to Jenkins. Subsequent normal stages
are skipped. Post-build diagnostics and project-specific cleanup still run.
A Gitleaks finding or scanner error marks its stage and overall build failed,
but later checks continue to collect evidence; see the continuation policy below.

The SonarScanner receives its token through the `SONAR_TOKEN` environment variable
provided by the existing Jenkins credential. Its command no longer ignores errors.
`sonar.qualitygate.wait=true` makes the scanner wait for the server's quality gate,
with a 300-second processing limit. A rejected gate, scanner error or gate timeout
fails the stage. This uses scanner-side polling rather than requiring a new Jenkins
Sonar plugin/webhook. See the [SonarSource quality gate documentation](https://docs.sonarsource.com/sonarqube-community-build/analyzing-source-code/ci-integration/overview).
The existing Sonar server URL and host-network setup remain unchanged; Jenkins must
be able to reach that server and its `asset-avengers` project must have the team's
intended quality gate configured. These settings do not create new quality rules.

Logs are cleared after checkout to prevent reports from reusing a prior build's
output. The final post-build cleanup condition archives available
`gitleaks-output.txt`, `services-output.txt`, `sonar-output.txt` and
`ci-docker-logs.txt`, including partial output on failures. Container logs are captured
before removing the initialized CI stack. Missing logs before their stage starts
are expected; archiving allows an empty set.

Run the controlled failure tests together with the isolation guards:

```bash
python3 -m unittest discover -s scripts/tests -p 'test_ci*.py' -v
```

These execute the real check script against substitute Docker/Compose commands,
checking nonzero failures, retained output, successful paths, missing credentials,
and failed log writes. They also check that the scanner is invoked with gate waiting.
They do not replace an actual Jenkins run against the team's SonarQube instance.


## Required application tests and coverage

The old Java preparation step used `-DskipTests`. Jenkins now runs these required
stages before SonarQube, through `scripts/ci-tests.sh`:

| Stage | What runs | Reports |
| --- | --- | --- |
| Java Tests and Coverage | Trading and internal APIs, using Maven/JDK 25 | Surefire JUnit XML and JaCoCo XML/HTML for each service |
| Authentication and UI Tests | NestJS tests on Node 24, followed by both Angular unit suites | JUnit XML and LCOV for each application |
| Pipeline and CI Guard Tests | Python report-schedule unit tests and CI failure/isolation guards | Console results |

All commands propagate failures; Jenkins skips subsequent normal stages after a
failed test. The final post condition publishes available JUnit results and archives
coverage, even if a later step fails. Old generated reports are removed after
checkout to avoid publishing stale successes on a reused workspace. Missing reports
are allowed when publishing an early failure, but the Sonar stage requires all five
application coverage reports before scanning.

JaCoCo 0.8.14 supports this project's Java 25 bytecode; see the
[JaCoCo release history](https://www.jacoco.org/jacoco/trunk/doc/changes.html).
Its agent runs during tests and its report goal runs in Maven's test phase.
Both Java services' compiled classes and dependencies are supplied to Sonar.
Vitest's V8 coverage provider is locked alongside the UI test dependencies.
`npm ci` installs the lockfile, and `npm run test:ci` disables interactive watch mode
and writes machine-readable results. Tests and generated reports are excluded from
Sonar's production source tree.

For example, both UIs contain `src/app` files. `scripts/ci-lcov.cjs` makes their LCOV
paths explicit as `frontend/src/...` or `internal-frontend/src/...` so Sonar maps
coverage to the correct application. It rejects absent, empty or invalid-source
LCOV reports. Authentication uses the same normalization.

### Authentication database tests

MFA, password-reset and SSO suites previously skipped without
`MFA_TEST_DATABASE_URL`. Jenkins now starts its own CI `auth-db`, verifies the
container's Compose project label and runs the auth test container in that DB's
network namespace. `scripts/ci-auth-tests.sh` derives the test URL from that
container's settings, waits for TCP readiness, then runs the suite. It uses no
published database port or development database URL. Email delivery is mocked in
the tests; the suite does not send real password-reset emails. Jenkins' initialized
project cleanup removes this database afterward.

### Running locally

For each Java service:

```bash
mvn -f backend/pom.xml clean test
mvn -f internal-backend/pom.xml clean test
```

Use JDK 25. In each UI or auth directory, run `npm ci` followed by
`npm run test:ci` with Node 24. Local auth tests skip the PostgreSQL suites unless

at saved application data. On a Jenkins agent, use the containerized helper stages;
the auth action requires the initialized CI project and its root environment file.
Do not run the containerized Node installs over a Mac's dependencies: the Linux
container installs platform-specific packages. Use the local commands on a Mac.

## Pull-request routes (problem 5)

Jenkins previously accepted only `dev` into `main`, leaving feature PRs into `dev`
without these checks. `scripts/ci-pr-policy.sh` now evaluates the Jenkins multibranch
metadata in the first stage, before loading application credentials or initializing
Docker. No feature-branch naming convention is required.

| Source | Target | Result |
| --- | --- | --- |
| `feature/CICD_Updates` | `dev` | Run checks |
| `fix/frontend-refactor` | `dev` | Run checks |
| Any other same-repository branch, including a `main` synchronization PR | `dev` | Run checks |
| `dev` | `main` | Run checks |
| Feature/fix branch | `main` | Skip: merge through `dev` first |
| Any branch | Other target | Skip |
| A normal branch build without PR metadata | Any | Skip |
| External fork PR | Any | Skip in this credentialed pipeline |

The helper requires nonempty `CHANGE_ID`, `CHANGE_BRANCH` and `CHANGE_TARGET`,
rejects self-targeting routes, and rejects nonempty `CHANGE_FORK`. Rejected jobs
are marked `NOT_BUILT` and stopped before credential generation. Accepted PRs run
the same required build, test, scan and quality-gate stages; this is not a lighter
feature-branch check. The pipeline still relies on Declarative Pipeline's automatic
SCM checkout to make the policy script available before the explicit checkout stage.

For example, open a PR from `feature/CICD_Updates` into `dev`. Jenkins should print
`Accepted pull request: feature/CICD_Updates -> dev` and proceed with the checks.
After integration, a `dev` into `main` release PR follows the same pipeline.

### Jenkins and repository configuration

The Jenkinsfile can accept only PR jobs that Jenkins actually discovers. In the
existing multibranch job, enable discovery of same-repository pull requests and
ensure any branch/PR discovery filters allow PRs targeting `dev` as well as `main`.
Configure the PR discovery strategy to test the proposed merge with its target,
then rescan the multibranch job after saving. Keep the Jenkins trust configuration
restricted appropriately for jobs that load shared credentials; the script's fork
check is a routing guard, not a sandbox for malicious pipeline code.

In the repository's branch rules, require this Jenkins job's reported status check
before merging into both `dev` and `main`. Use the actual check name reported by
your Jenkins integration. The Jenkinsfile does not configure branch protection or
change the Jenkins server's discovery settings.

The policy tests cover feature/fix/hotfix and arbitrary branch names, release and
synchronization PRs, unsupported targets, missing metadata and external forks:

```bash
python3 -m unittest discover -s scripts/tests -p test_ci_pr_policy.py -v
```

Six new tests passed; all 24 CI guards passed together on October 22, 2026. Live PR
job discovery and status reporting still need verification on the Jenkins server.
Staff/reporting image coverage and temporary environment settings are now included
in the problem 4 stages documented below.

## Development database resets

Development uses the existing SQL schema files directly. After changing a schema,
the team's disposable-data workflow is to run `bash scripts/stop-project.sh`,
choose `y` to delete saved database storage, then run `bash scripts/start-project.sh`.
This creates fresh databases from the updated schemas and discards saved users,
trades and reports. Choosing `no` or Enter preserves existing storage instead.
Startup also explicitly applies the current schema files to existing databases;
`CREATE TABLE IF NOT EXISTS` alone does not add columns to an existing table, so
preserving data requires appropriate `ALTER TABLE` statements in those files.

There is no custom versioned migration runner or database-upgrade CI stage. CI
resource isolation, required scan failures, test/coverage reporting and PR routing
remain enabled. A migration tool can be considered when upgrades must reliably
preserve long-lived user data. Python test tools run in their existing container;
the removed upgrade check no longer requires Python installed on the Jenkins host.


## Readiness instead of fixed delays (problem 7)

This Jenkinsfile validates PRs using temporary containers. **It does not deploy the
application**, publish images to a registry, or leave a serving stack running after
success. Success notifications now say this explicitly. Continue using the normal
startup script to run the development application. Production deployment would be
a separate workflow with a defined target, credentials and release policy.

The old pipeline slept ten seconds and checked `docker compose ps`. That command
can succeed while an application is still starting or its database is unavailable.
The existing `scripts/ci-checks.sh` now performs these checks without adding another
helper script:

| Check | Passing condition |
| --- | --- |
| Trading PostgreSQL | Container health is healthy; its healthcheck executes SQL against the configured DB over TCP |
| Auth PostgreSQL | Same SQL-backed health requirement |
| Auth server | Existing Docker healthcheck gets success from `/health/ready`, which queries its database |
| Trading API | A request from the auth container on the CI network receives HTTP success and `status: UP` from `/actuator/health/readiness` |
| Client Nginx | Fetching `/index.html` inside the frontend container succeeds |

Spring Boot Actuator supplies the trading readiness endpoint. Its readiness group
includes `readinessState` and `db`, so an HTTP listener alone is insufficient.
Only GET `/actuator/health/readiness` is publicly allowed; its response exposes
status without dependency details. Other management URLs remain denied by the
existing security rules. See [Spring Boot health groups and probes](https://docs.spring.io/spring-boot/4.2/reference/actuator/endpoints.html).
The trading probe uses the Node runtime already present in the auth container;
the client probe uses Nginx Alpine's existing wget. No new diagnostic container,
host port or curl installation is needed.

The database-start stage waits for database health before continuing. After service
startup completes, readiness checks share a 180-second budget; only unsuccessful
checks retry, at two-second intervals. The HTTP requests have five-second timeouts.
`CI_READY_TIMEOUT_SECONDS` optionally changes that budget (1–999) in Jenkins; no
new root `.env` entry is required. A missing/stopped container or a missing expected
healthcheck fails immediately. A still-unhealthy or nonresponsive application fails
when the budget expires. Docker operations themselves remain bounded by Jenkins'
existing overall pipeline timeout.

After the tests and Sonar gate, **Verify Service Readiness** performs the checks again
to catch a service that stopped during testing. Status messages identify which
service is being checked. Startup readiness output stays in `services-output.txt`;
the final recheck writes `readiness-output.txt`. Both are available in console output
and archived with the other diagnostics. Container logs are still saved before
project-specific teardown after failure or success.

These are dependency/startup checks, not a complete browser or trading workflow.
These readiness probes do not call Fauxnance, buy shares or send email. Staff
integration is covered by its separate stage below.
Internal CI credentials, MFA encryption and SSO settings are now generated by the
CI environment stage, as described below.

Controlled tests cover immediate readiness, delayed database readiness, stopped
containers, absent healthchecks, health timeouts, HTTP timeouts and failure exit
codes. Spring tests verify a public status-only readiness response, HTTP 503 when
database health fails or the application refuses traffic, and continued protection
of other management endpoints. A live Jenkins run is still required to validate the
complete container setup on the team's agent.

flags, `--quiet`, or YAML `!reset` tags. Normal staff configuration uses the
`version: "3.8"` format and puts its existing project name in the CLI:

```bash
docker compose -p asset-avengers-internal --env-file .env \
  -f deployment/admin-analytics/admin-analyst-stack.compose.yml up -d --build
```

preserves the original reporting/Kafka volume and internal network identities;

do not stop containers, reset data or change the trading network name.

script or permanent duplicate stack configuration is introduced.

health must be ready, one-shot Kafka/Superset initialization jobs must exit zero,

health and Superset health endpoints. Readiness has a 300-second budget with
conditional two-second retries. Stopped services, failed initializers and timeout

## Staff/reporting builds and temporary configuration (problem 4)

Jenkins now requires these stages before SonarQube:

1. **Build Staff and Reporting Images** builds internal Spring API, staff Angular UI,
   Python pipeline and custom Superset images from their own Dockerfiles. Tests run
   separately; each image build must succeed as well.
2. **Staff Reporting Integration** starts the existing isolated verifier with those
   exact images, waits for readiness, seeds a simulated source fill and checks real
   Kafka delivery, report publication, staff API role restrictions, Nginx forwarding,
   Superset guest tokens and a real chart-data query. It does not use live records.

`scripts/ci-checks.sh` owns the new actions; no additional helper script is needed.
The four images use `${CI_PROJECT_NAME}` as their tag, rather than replacing the
team's `:local` images. Normal deployment still defaults to `STAFF_IMAGE_TAG=local`
in root `.env.example`. The test stack's project is `${CI_PROJECT_NAME}-staff`, with
its own databases, Kafka volume and networks, and no published host ports. Images
and Docker's build cache remain available after teardown; CI does not globally prune.

### Settings and Jenkins prerequisites

**Generate Temporary CI Settings** creates a mode-600 root `.env` in the Jenkins
workspace using Python's cryptographic secrets generator. Each build receives fresh
trading/auth passwords and JWT, MFA encryption and SSO secrets. MFA's encryption key
is a base64-encoded 32-byte value. Database names/users are non-secret fixture values.
The staff verifier independently generates reporting/Superset database passwords,
metadata passwords, guest/session secrets and service-user credentials. It reads
only the SSO value it needs from the disposable CI environment file, so auth and the
staff Superset configuration receive the same SSO secret.

Required Jenkins credentials are now `FAUXNANCE_KEY` and `SONAR_TOKEN`; internal
DB/JWT values no longer require saved Jenkins credentials. Existing optional email
notification settings are unchanged. No Resend credential or real email delivery is
needed for these tests. Build agents need Python 3, Bash, Docker and the
`docker compose` plugin, plus dependency/registry access and enough RAM/disk for
Kafka, Superset and both temporary stacks. The existing overall 30-minute pipeline
timeout remains; observe cold-cache builds on the actual agent.

The generated `.env` belongs only to the Jenkins checkout: CI does not change the
root `.env` used by a running developer stack. It is not printed or archived and is
removed in post-build handling when generation succeeds. Do not point a Jenkins
workspace at the checkout used to run a persistent developer stack.

### Logs, failure handling and cleanup

Image output is archived as `staff-build-output.txt`, integration output as
`staff-integration-output.txt`, and failures capture staff container diagnostics in
`staff-docker-logs.txt`. Required failures propagate to Jenkins. The verifier always
attempts teardown and maps SIGTERM to normal finally cleanup. Jenkins additionally
retries `staff-cleanup` using the exact validated CI project name, even if verification
was interrupted; cleanup mode never starts services. It preserves previously saved
failure logs. Client cleanup is attempted even if staff teardown fails. This job
continues to validate PRs, without deploying or publishing images to a registry.

The API integration checks use short-lived, test-signed staff JWTs. They are followed
by browser checks using real passwords, MFA and SSO without injecting those JWTs.
Auth MFA/reset/SSO PostgreSQL service tests still run in their separate stage.
The real staff browser authentication check is now required within that stage,
as described below.

## Temporary Playwright browser authentication

**Staff Integration and Browser Authentication** now runs a real headless Chromium
journey after the Kafka/reporting/API checks, before tearing the stack down.
`scripts/ci-checks.sh` obtains the auth image already built for this CI project and
passes it to the verifier. The browser-only Compose override starts that image with
a fresh auth database and a fresh MFA encryption key. It shares the test stack's
JWT and SSO secrets, never a developer's saved auth database.

The verifier provisions two temporary staff identities with a new random password.
Only provisioning uses SQL. Browser sign-in then uses the normal Nginx proxy and
unmodified auth endpoints. `internal-frontend/tests/auth-journey.e2e.ts` checks:

- Wrong password rejection.
- Admin and analyst enrollment via the visible QR/manual setup component.
- Real six-digit TOTP verification from each freshly issued enrollment secret.
- Recovery-code acknowledgment and correct role-specific workspace visibility.
- Explicit logout followed by a fresh MFA challenge, with no repeated enrollment.
- Wrong authenticator-code rejection and acceptance of a new, unconsumed code.
- Analyst clicks Open Superset workspace, completes the actual one-use ticket
  exchange, reaches SQL Lab, and authenticates through Superset's real session cookie.
- Staff logout invalidates that Superset author session on its next request.

No permanent MFA seed, pre-enrolled test account or browser-injected JWT is used.
TOTP may wait up to one 30-second period before reuse tests, because the application
correctly rejects an already consumed code. This is different from a startup delay.
The client signup/password-reset browser journeys are not added by this staff test;
the existing client unit tests and auth database tests remain in place.

The test uses a temporary official Playwright Docker image matching the exact
`@playwright/test` version in the staff lockfile. See [Playwright Docker guidance](https://playwright.dev/docs/next/docker).
It installs the locked test dependencies inside its disposable filesystem, uses the
private stack network, publishes no host ports and mounts no Docker socket. Chromium
gets a 1 GiB shared-memory allocation. Jenkins needs no host browser installation.
The agent needs registry/npm access and additional disk/RAM for the browser image.
The isolated fixture limits Kafka's heap to 256 MiB and the staff Java service's
heap to 384 MiB. After ingestion checks pass, the verifier stops its own Kafka,
publisher, consumer, reporting worker and source database before launching Chromium.
The auth, staff, reporting database and Superset services stay running for the browser
journey. These settings do not change the development or deployment stack.

JUnit results and masked failure screenshots go under
`internal-frontend/test-results/browser/` and are published by Jenkins. Full traces,
videos and automatic screenshots are disabled because enrollment/recovery screens
and network responses contain credentials. The failure hook masks/scrubs secret
fields; the runner deletes Playwright's unmasked accessibility snapshot files.
Jenkins archives only the browser XML and PNG files, not the raw DOM snapshots.

The verifier removes the exact temporary browser container even on timeout, then
tears down the auth/staff stack. Jenkins' fallback cleanup includes the browser-only
services and never starts them. The image itself is a reusable Docker cache, not a
permanent running application service.

For a local run after building the four staff images and an auth image:

```bash
python3 scripts/verify-admin-stack.py --browser --auth-image YOUR_AUTH_IMAGE
```

Jenkins supplies project-specific image/project arguments automatically. The existing
`playwright.config.ts` dev-server tests remain separate from `playwright.ci.config.ts`;

## Reviewed Gitleaks false positives and continued checks

The scanner explicitly loads root `.gitleaks.toml` and extends all built-in rules.
Two exact public dummy signing-key values are allowed across files so reusable
fixtures do not repeatedly fail scanning. These values must never be used as real
deployment credentials. A different value, including a suffix added to a dummy key,
is not exempt. There is no whole-file, test-folder or generic JWT exclusion.

Reviewed historical documentation, test and PDF-verifier findings are listed in
`.gitleaksignore` using exact commit/file/rule/line fingerprints. Jenkins explicitly
passes `--gitleaks-ignore-path /repo/.gitleaksignore` because the scanner runs in a
container whose working directory may differ from the mounted repository. The
redundant path/full-line allowlists were removed from `.gitleaks.toml`; the existing
historical fingerprint list is preserved. New prose/variable findings still need
review. Full-history scanning and built-in detection remain enabled.

The Jenkins Gitleaks stage catches scanner failures, marks the stage and overall
build FAILURE, and continues to later checks to collect test/coverage evidence.
Other required failures still stop later normal stages. User aborts and timeouts
are not swallowed. Scanner/runtime errors also leave a failed build and allow
later checks; inspect the scan log to distinguish an error from a finding. This
change never converts a detected secret into a successful build or authorizes a
merge/deployment. Success emails cannot run for that failed result; notifications
use configured EMAIL_1 through EMAIL_5 recipients.

## Runtime project name and cleanup state

The generated `CI_PROJECT_NAME` and the initialization/settings/staff cleanup flags
are assigned through `env` inside script blocks, not the Declarative `environment`
directive. A Declarative blank/false default can shadow later imperative values:
the name generator succeeds but the next shell still receives a blank name, so
`ci-compose.sh init` correctly rejects it. The same issue can prevent cleanup flags
from becoming true. Initialize these mutable values in the first script block,
then set them only as each operation succeeds. The helper's strict name/receipt
validation remains enabled. Jenkins also validates the generated name before init.

Guards exercise generated-name-to-init handoff and reject reintroducing shadowing
in the Jenkinsfile. These local checks do not execute Jenkins itself; rerun the
updated PR build on the actual server to verify environment propagation and cleanup.

## Shell launch failure: argument list too long

If Jenkins reports `Cannot run program "nohup": error=7, Argument list too long`
after image builds, check for bulk logs assigned to `env`. Jenkins passes those
values to every child process. A large Docker build log can exceed Linux's
argument/environment size limits before even a short shell command starts.

Build and scanner output now stay in `services-output.txt` and
`gitleaks-output.txt`, streamed through `tee` and archived with other diagnostics.
They are not assigned to `env.SERVICES_OUTPUT` or `env.GITLEAKS_OUTPUT`. Small
project names and cleanup flags still use the process environment. Regression
guards check that log export does not return and capture/publication remains wired.

Start a fresh build after updating the PR checkout. Replaying or resuming an old
build can retain the previous pipeline state. This fix does not require changing
`nohup`, installing a package, disabling tests or increasing OS limits. If the
updated build still fails, inspect other inherited environment sizes without
printing their secret values. No new full Jenkins run was performed locally.

The aggregate-account overview requires aggregate signals and refresh methods in

## Maven dependency descriptor failures

The Java action uses Maven `-e` to include nested causes when a plugin or artifact
cannot resolve. A downloaded child POM does not prove its parent POM resolved.
For example, the dependency-copy plugin can report a descriptor failure for
maven-resolver-util even after downloading that POM if its maven-resolver parent
cannot be resolved. Check the nested Caused by/transfer response before changing
versions, certificates or proxy settings. Error diagnostics remain enabled without
Maven `-X` debug output, which is unnecessary as the initial troubleshooting step.

Each current Java test container uses `/tmp/maven-repository` inside its disposable
filesystem, so a new run does not reuse the old container's failed-download cache.
Do not delete saved databases or disable tests to address a dependency download.
Retry once for a possible transient failure; if it repeats, use the detailed error
to identify repository availability, DNS, TLS, proxy, HTTP status or POM issues.
Enabling diagnostics is not itself proof that the remote build problem is fixed.

## Email parameter warnings versus SMTP connection failures

The Email Extension Pipeline step does not accept separate `cc` and `bcc` fields.
Those unsupported fields were removed; configured EMAIL_1 through EMAIL_5 recipients are passed via `to` and no
recipient providers are selected. This removes parameter warnings but does not
repair SMTP connectivity. Email Extension has its own Extended E-mail Notification
settings; configuring only the separate E-mail Notification section may not
configure `emailext`.

For Gmail SMTP, configure smtp.gmail.com, STARTTLS on port 587, authentication with
the sender's full email and an eligible Google App Password (not the ordinary
account password). Verify outbound access from the Jenkins controller environment,
including its container, not just the host or build agent. Inspect the detailed
SMTP exception to distinguish timeouts, DNS, TLS and authentication failures.
Receiving a Sending email to message confirms recipient selection, not delivery.
No real SMTP delivery was tested from this development machine.
